# 首次签发攻坚记录（2026-10-25 更新）

> 结论先行：**签发本身是纯 HTTP。唯一必须依赖浏览器的是生成 `p`。**
> 而 `p` 是一次性的，所以"一次 mint + 无限续期"仍是最优架构。

## 一、本轮决定性发现

### 1. `p` 严格一次性（三连提交实测）

捕获一个未被消耗的 fresh `p`，用纯 curl 连提交三次：

| 提交 | POST 状态 | POST `x-iinfo` | 签发 token | 页面验证 |
|---|---|---|---|---|
| #1 | 200 | `q(0 0 0 -1) r(0 0)` | 1282 | **SPA 160903** ✅ |
| #2 | 200 | `q(0 0 0 -1) r(1 1)` | 1266 | 6058 失效 |
| #3 | 200 | `q(0 0 1 -1) r(2 2)` | 1266 | 6058 失效 |

**服务端每次都返回 200 并签发 token，但只有首次使用 `p` 的 token 有效。**
注意 #2/#3 的 `x-iinfo` 反而更好看（`r(1 1)`/`r(2 2)`），
**所以 `r(N N)` 不能作为 token 有效性的判据**——必须做页面验证。

### 2. fresh `p` 的纯 curl 重放 100% 成功

拦截浏览器 POST 使其不发出（`route.abort()`），把 body 存盘，再用 curl 提交：

```
captured fresh solution: 28942 bytes (POST aborted)
POST: HTTP 200  q(0 0 0 -1) r(1 1)
token len=1278 renewInSec=781
VERIFY: HTTP 200 160903 bytes  kind=spa   r(3 3) U12
```

**完全纯 HTTP，无需任何浏览器参与提交。**

### 3. `performance` 字段完全不校验

对 fresh `p` 做信封级消融（每个变体各用一个新 `p`）：

| 变体 | POST | token | 页面验证 |
|---|---|---|---|
| A 对照 | `r(2 2)` | 1258 | **SPA 160903** |
| B `performance` = `{"total":0}` | `r(2 2)` | 1262 | **SPA 160903** ✅ |
| C `og=1, st-=1000` | `r(0 0)` | **902** | 6058 失效 |

- `performance` **随便填，不影响结果**（省掉一个怀疑方向）
- `st`/`og` **参与校验**，而且被编进 `p`（token 从 1258 缩到 902）

### 4. `p` 是完全加密的不透明块

对 21132 字节解码后做结构扫描：

| 检查项 | 结果 |
|---|---|
| zlib/gzip/brotli/zstd magic | 只有随机字节巧合，解压全失败 |
| base64 字母表连续段 ≥16 | **0 段** |
| 可打印 ASCII 连续段 ≥20 | **0 段** |
| 重复 4 字节标记 | 无有意义的重复结构 |

> 踩坑提醒：`p` 的**字符串**里能看到看似 base64 的长串，那只是
> base64 输出本身落在字母表内的必然结果，不是嵌套编码。解码后无任何结构。

**结论：`p` 无法离线编辑，内容分析这条路彻底关闭。**

## 二、403 / 6058 / SPA 三种判定的精确语义

| 情形 | HTTP | 大小 | `x-iinfo` 特征 |
|---|---|---|---|
| 真实 token | 200 | 160903 | `pNNN … q(0 0 0 -1) r(3 3) U12` |
| **iv8 token** | **403** | **969** | `pNNN … q(0 -1 -1 -1) r(0 -1) B15(14,0,0) U18` |
| 已消耗/过期 token | 200 | 6058 | `pNNN … r(0 -1) B10(14,0,0) U18` |

- 403 页带 `edet=15`、`rpinfo=594`、`Incapsula incident ID`
- 6058 是挑战插页（`scriptElement.src`），表示"当无效处理"
- iv8 走的是 **403 主动拒绝**，不是 6058。说明服务端能解开 `p`，
  判定其内容为 bot，而非格式错误。

## 三、iv8 的 Canvas 是静态假值（曾被误判为根因）

画三种完全不同的图形：

```
画 A：白底 + 黑字 AAAA   → 1318 字符
画 B：红底 + 黑色圆形    → 1318 字符
画 C：蓝底纯色           → 1318 字符
A == B == C == True
```

iv8 内置五种 canvas 模式全部返回空或静态：

| `config.canvas.fingerprint.mode` | 结果 |
|---|---|
| `clear` / `noise` / `random` / `fuzzy` / `hash` | 全部 0 长度 |

**iv8 不执行真实光栅化**，无法产生随绘制内容变化的 PNG。

### 已做的补救：Canvas 读取点回放

抓取真实浏览器的 439 条 canvas 调用与全部读取点，生成
`js_reverse_cache/canvas_replay.js`，按 canvas 尺寸回放真实值：

| 读取点 | canvas 尺寸 | 真实输出 |
|---|---|---|
| `toDataURL('image/webp')` | 1×1 | 123 字符 |
| `getImageData(595,155,4,4)` | 4×4 | 64 字节 |
| `toDataURL()` | 4×4 | 118 字符 |
| `getImageData(0,0,5,5)` | 5×5 | 100 字节 |
| `toDataURL()` | 5×5 | 182 字符 |

同时回放 183 个字体测量值（61 字体族 × 3 回退）。

**效果**：token `seg4` 从 816~830 涨到 **1124**（超过真实的 750~800），
`p` 变大，但页面**仍然 403**。

→ Canvas 不是唯一缺口。

## 四、已证伪的假设（全部实测）

| 假设 | 实验 | 结论 |
|---|---|---|
| token 绑 UA/TLS | 真 token × 4 组 TLS/UA 组合 | 全部 SPA，不绑 |
| token 绑 session cookie | 同 session / 新 session 交叉 | 不绑 |
| 需要 UTMVC（`SWJIYLWA`+`SWKMTFSR`） | 签发后补这两个请求 | 仍 403 |
| `old_token` 是绑定凭证 | 真 token 塞进 iv8 solution | `r(2 2)`，仍 403 |
| iv8 token 可经续期洗白 | `renew_token(iv8_token)` | `renewInSec=845`，仍 403 |
| 缺 `xctrc` / `prxCookie` | 单独/同时补 | 仍 403 |
| `performance` 被校验 | fresh `p` 清空 performance | **SPA 通过**（不校验） |
| 签发后多余 POST 触发风控 | 拿到 token 立刻停事件循环 | 仍 403 |
| `p` 有可编辑结构 | 21132 字节全量结构扫描 | 完全加密，无结构 |
| `p` 可重复使用 | 同一 `p` 连提交 3 次 | **严格一次性** |
| 段拼接可绕过 | real/iv8 各段交叉拼接 | 全 6058（MAC 绑定） |

## 五、为什么纯协议首签仍然不通

```
第 1 层 solution POST：校验 p 的签名/格式 → r(1 1) + 签发 token  ✅ iv8 通过
第 2 层 页面 GET     ：解开 p 读取指纹内容 → 判定 bot → 403      ❌ iv8 失败
```

iv8 过第 1 层恰恰证明**加密实现完全正确**。卡在第 2 层的
**`p` 内的指纹内容**。`p` 完全加密，无法逐字段比对或修正。

### 与阿里 V2 案例的本质差异

| | 阿里 V2 (pzds) | 本站 Reese84 |
|---|---|---|
| 载荷生成 | 本地 Node 跑**原站 WASM** | iv8 跑 `challenge.js` |
| 载荷格式 | WASM 导出二进制 + JS 封装 | `bin1` + 全加密块 |
| 核心熵源 | **无**（`field21` 纯算法可逆） | **浏览器运行时遥测** |
| 能否纯算 | 能 | 不能 |

阿里 V2 能纯算，是因为载荷压在单个 WASM 导出函数上、不含渲染熵。
Reese84 的 `p` 直接承载 Canvas/WebGL/音频/字体等**运行时渲染结果**。

### 从案例学到的重要纠正

1. **canvas 不是卡点**。案例完全不做 canvas 处理。我之前补 canvas 回放
   （注入真实 Firefox PNG 到 Chrome UA 环境）方向错误，甚至可能有害。
2. **OAuth 200 不是有效判据**。实测：用垃圾 token
   `3:AAAA…:BBBB:CCCC:DDDD:` 请求 OAuth 也返回 200 + access_token。
   OAuth 完全不校验 `x-d-token`。案例把 OAuth 200 当作流程一环，
   但它证明不了 token 有效。
3. **air-bounds 才是真判据**。已建立正向对照：新鲜真实 token →
   air-bounds 200，6 组 / 12 班。iv8 token → air-bounds 403。

## 七、本轮新增的实证（会话绑定与 API 门）

### OAuth 不校验 token

| token | OAuth |
|---|---|
| 垃圾 token | **200 + access_token** |
| iv8 token | 200 + access_token |
| 真实 token | 200 + access_token |

### iv8 token 在 4 种会话绑定下全部 403

| 组合 | 页面 | air-bounds |
|---|---|---|
| A. 全新 session，只带 reese84 | 403 | 403 |
| B. 跑 challenge 的同一 session（带其 incap cookies） | 403 | 403 |
| C. 真实浏览器 incap cookies + iv8 token | 403 | 403 |
| D. 真实浏览器完整 cookie 集 + iv8 token | 403 | 403 |

→ **token 不绑定 session。**

### st / sr 的观察

两次独立真实捕获：`st=1792932974`、`sr=3906300928` **完全相同**，只有 `cr` 变化。
iv8 产生 `st=1792935675`、`sr=1869597566`。

但 challenge 路径是轮换的（`aC_NUjD…` → `uBrBtg6…`），`st`/`sr` 很可能是
**跟着 challenge 实例走**（同 challenge 缓存 → 同 st/sr），所以两次真实捕获
相同只是拿到同一个缓存 challenge。**不能据此判定 iv8 的 st/sr 错误。**

`st`/`sr` 在脚本里不是字面量（脚本含 SHA-1 常量表），是运行时计算。


```
[一次性] 浏览器 mint 种子 token（约 15 秒）
     ↓
[纯 Python] 续期链 → OAuth → air-bounds → 解析票价
     ↑______________ 无限循环 ______________|
```

**为什么这是最优**：`p` 一次性 → 每个 token 都需要一个新 `p` →
而生成 `p` 必须真实渲染 → 所以"每个 token 一次浏览器"是下界。
续期链绕开了 `p` 的重新生成，因此严格优于任何 `p` 捕获方案。

实测：续期链 8 跳全通，每跳 45 个报价；
单程 BKK→HKT 最低 2830 THB；商务舱 `PGBLUE` D 舱 6280 THB。

## 八、若仍要攻纯协议首签，只剩两条路

### 路线 1：把 Canvas/WebGL 光栅化转发到真实渲染器（中等成本）

iv8 无渲染器，但可以把绘制命令序列化后交给外部渲染：

- 拦截 `CanvasRenderingContext2D` 全部绘制方法，记录调用序列
- 用离屏真实渲染器（Camoufox 的 canvas）重放，取回真实 PNG/像素
- 注入 iv8

已完成的铺垫：439 条调用序列、6 个读取点、183 字体测量值全部落盘
（`js_reverse_cache/canvas_calls.json`、`canvas_replay.js`、`real_fp_dump.json`）。

仍需补：WebGL（renderer/vendor/扩展列表）、AudioContext、更多尺寸组合。
工作量中等，**不涉及加密逆向**，且能产生真实亚像素差异。

### 路线 2：反混淆 `challenge.js` 定位校验点（高成本，不保证成功）

835KB obfuscator.io。目标是找出 `p` 内哪些字段参与服务端比对，
把需要真实的熵源从"全部"缩小到"几项"。每次请求动态生成，难度高。

### 路线 3：接受现状（零成本，已可用）

一次 mint + 无限续期。`renewInSec` 每次 300~900 秒，可长期存活。
