## 一、结论先说

| 项目 | 状态 |
|---|---|
| 纯 Python 取到机票与运价 | ✅ **已完成并实测通过** |
| 单程 / 往返 | ✅ 都支持 |

| **首次 token 完全无浏览器** | ❌ **未达标**（入口已找到，载荷未攻破） |

关键突破：**Reese84 的"续期"不校验指纹**。首次签发需要完整浏览器指纹，
但只要有一个真 token，后续可以纯 HTTP 无限续期。所以架构是：

```
[一次性] 浏览器 mint 种子 token
     ↓
[纯 Python] 续期 → 换新 token → OAuth → air-bounds → 解析票价
     ↑__________________ 循环续期 __________________|
```

### 1.1 首签攻防的当前状态（2026-10-25）

**本轮新发现：真实入口是 `{"f":"gpc"}`，不是 `{"f":"1.1"}`。**

```
POST /<random-path>?d=digital.bangkokair.com   body={"f":"gpc"}   -> 200 / 406B
     响应 = base64( {"c":"{\"t\":4294967295,\"d\":\"<hex40>\",\"s\":\"<hex32>\"}",
                    "s":"<176 chars>"} )
POST /<random-path>?d=digital.bangkokair.com   body={"solution":{...},"old_token":"3:...",...}
     -> {"token":"3:...","renewInSec":703,"cookieDomain":"bangkokair.com"}

POST {"f":"1.1"}   -> 400   ← 之前一直在用的错误入口
```

`{"f":"gpc"}` 纯 Python 就能打（200/406B），所以**入口不是瓶颈，载荷才是**。

**CDN 层拒绝证据（`x-iinfo` 响应头）**：

| 场景 | `x-iinfo` 片段 | 页面 |
|---|---|---|
| 无 cookie | `q(0 -1 -1 -1) r(0 -1)` | block 6058B |
| iv8 token | `q(0 -1 -1 -1) r(1 -1)` | block 6058B（`r(1,-1)` 即 1 次被拒） |
| 真实 token | `q(0 1 1 -1) r(4 4)` | **spa 161036B** |

**`p` 载荷头部差异**：

| 来源 | `p` base64 前缀 | 解码后 |
|---|---|---|
| 真实浏览器 | `YmluMTr` / `YmluMZ` | `bin1:` / `bin1\x98` |
| iv8 | `YmluMQB8` | **`bin1\x00\|`** |

`p` = base64(`"bin1"` + 密文)，iv8 在 `bin1` 后多写了 `0x00 0x7C`，
说明内部数据结构与真实浏览器不同。

**消融实验（固定 iv8 载荷，只改一个维度）全部失败**：

| 变体 | renewInSec | 页面 |
|---|---|---|
| iv8 原样 | 736 | 403 block |
| `st=0` | 760 | 403 block |
| `og=1` | 815 | 403 block |
| performance 补到 38 条 | 716 | 403 block |
| old_token + performance | 750 | 403 block |

**关键洞察**：`renewInSec` 恒为 700~800（服务端认为 token「有效」），
但页面仍 403。说明服务端**分两级判定**：

- 级别 1（续期接口）：只看 token 结构 → 永远给 `renewInSec>0`
- 级别 2（页面/API，CDN 层）：校验 token 与本次会话/指纹的绑定 → iv8 令牌在此被拒

因此 `renewInSec>0` **不能**作为 token 有效的判据（已修正 `verify_token`）。

## 二、核心发现：token 续期协议

### 2.1 请求

```
GET  /booking/availability/0                       （不带 reese84 cookie）
     -> 200 插页，含随机路径：scriptElement.src = "<path>"

POST /<random-path>?d=digital.bangkokair.com
     Content-Type: text/plain; charset=utf-8
     Accept: application/json; charset=utf-8
     Origin: https://digital.bangkokair.com
     Referer: https://digital.bangkokair.com/booking/availability/0

     body = "3:VB4I27k...DTVaz:"        ← 注意：只是一个 JSON 字符串字面量（旧 token）
```

### 2.2 响应

```json
{"token": "3:...", "renewInSec": 842, "cookieDomain": "bangkokair.com"}
```

- `renewInSec > 0` → 真 token，可用
- `renewInSec == 0` → 占位 token，无效

### 2.3 实测行为矩阵
| 请求体 | 响应 | 是否可用 |
|---|---|---|
| `"<真 token>"` | token 1154~1270 字符，`renewInSec 495~898` | ✅ 可用，且可链式续期 |
| `null` | token 418 字符，`renewInSec 0` | ❌ 无效 |
| `""` | `{"token":"","renewInSec":0}` | ❌ |
| `"<乱码>"` | 原样回显，`renewInSec 0` | ❌ |
| `{}` / `{"old_token":null}` | HTTP 400 | ❌ |

带新 token 访问页面 → **200 / 161036 字节 / `title="Booking"`**（真 SPA，非拦截页）。

### 3.5 运价族的两层结构 ★ 关键修正

响应里有两类"运价族"，**不能混用**：

| 层 | 字段 | 值 | 用途 |
|---|---|---|---|
| 商务运价族 | 请求参数 `commercialFareFamilies[]` | `PGPROMO`, `PGFLEX` | 决定检索哪套票价体系 |
| 子运价族 | 响应 `airBounds[].fareFamilyCode` | `PGPROMO`, `PGSAVER`, `PGFREEDOM`, `PGBLUE` | 用于结果筛选 |

实测验证（BKK→HKT 2026-11-20）：

```

PGFLEX   -> 200  47 bounds  codes=['PGFREEDOM','PGPROMO','PGSAVER']   ← 与 PGPROMO 结果完全一致
PGSAVER  -> 200   0 bounds  36917 INVALID COMMERCIAL FARE FAMILY
PGFREEDOM-> 200   0 bounds  36917 INVALID COMMERCIAL FARE FAMILY
PGBLUE   -> 200   0 bounds  36917 INVALID COMMERCIAL FARE FAMILY
PGBUSINESS/PGPREMIUM/PGFLEX... 见下
```

已穷举 18 个候选名，只有 `PGPROMO` 与 `PGFLEX` 有效（后者结果与前者逐字节等价的报价列表）。

`fareFamilyWithServices` 字典暴露了映射关系：


### 3.6 舱位与子运价族的强绑定 ★ 易踩坑

跨 6 条航线 × 3 个日期共 520 条报价的统计：

| 子运价族 | eco | business |
|---|---|---|
| PGFREEDOM | 245 | 4 |
| PGSAVER | 177 | 2 |
| PGPROMO | 76 | 2 |
| **PGBLUE** | **0** | **14** |

结论：
- **`PGBLUE` 只存在于商务舱**，且只在 ATR 机型航线（本样本仅 `BKK-USM`）
- `PGPROMO`/`PGSAVER`/`PGFREEDOM` 主要在经济舱
- **`--fare-code PGBLUE --cabin eco` 永远返回 0 条**，看起来像"售罄"，实际是该组合不存在

因此 `main.py` 内置 `CODE_CABIN` 映射，检测到冲突时自动纠正并告警：

```
warning: PGBLUE only exists in the business cabin; ignoring --cabin eco
```

### 3.7 error 1112 INVALID ITINERARY

往返时若 **返程日期早于去程日期**，API 返回 `400 / 1112 INVALID ITINERARY`。
`main.py` 在 CLI 层提前拦截并给出可读提示，不浪费一次网络往返。

### 3.8 错误响应必须显式识别 ★ 曾经的假通过

`air-bounds` 在参数非法时返回 **HTTP 200 + `{"errors":[...]}`**，没有 `data`：

```json
{"errors":[{"code":"36917","title":"INVALID COMMERCIAL FARE FAMILY",
            "source":{"parameter":"commercialFareFamilies"}}]}
```

早期版本直接 `parse_offers()` 得到空列表并当成"0 报价"正常返回，
导致 20 个用例里 13 个是**假通过**。现已修复：`_air_bounds_call()` 检测到
`errors` 立即抛 `Reese84Error`。

## 四、为什么 iv8 首次签发不可行（已彻底查清）

同一份 Python 代码、同样的 headers/cookies/TLS：

| token 来源 | 结果 |
|---|---|
| 真实浏览器 mint | **200 / 160903 字节**（SPA） |
| iv8 mint | **403 / 970 字节** + `SWJIYLWA` |

→ 问题是 **token 内容**，不是请求侧。已逐项排除：

| 假设 | 验证方式 | 结果 |
|---|---|---|
| cookie 编码 | raw / percent-encoded / 只带 reese84 | 都失败 |
| cookie domain | host-only / `.bangkokair.com` | 都失败 |
| UA | Chrome 136 / Firefox 135 | 都失败 |
| TLS | chrome136 / firefox135 / firefox133 | 都失败 |
| 请求头 | 补全 UA/sec-ch-ua/Origin/Referer/sec-fetch-* | 失败 |
| token 分段 | `3:<24>:<152|172>:<44>:<1016|1076>:` 结构一致 | 不是原因 |
| incap_ses 轮换 | 阻断 token 后的第三次 `{"f":"1.1"}` POST | 不是原因 |
| `document.all` | iv8 已符合 HTMLDDA 全部语义 | 不是原因 |
| 全 Firefox 身份 | UA/vendor/productSub/buildID/oscpu/userAgentData/chrome/screen/hw/WebGL/Intl 全对齐 | 仍 403 |
| token 响应字段 | 只有 `{token, renewInSec, cookieDomain}`，与浏览器一致 | 不是原因 |
| window 属性枚举 | 加 258 个假全局 → p_len **-92 字节** | 不是原因 |

**唯一差异**：载荷 `p` 比真实浏览器大（iv8 ~30000 原始字节 vs 浏览器 17628）。

### `p` 载荷分析（JS 层手段已穷尽）

`p` = `base64("bin1" + 密文)`，密文长度 == 明文长度，明文是 `Uint8Array`。

| 抓明文手段 | 结果 |
|---|---|
| `charCodeAt` hook | 只抓到脚本内部字符串表（507186 字符）与 WASM（7208B） |
| `String.fromCharCode` (>5000 args) | 从未调用 |
| `btoa` hook | 拿到的是密文 |
| `Uint8Array` 构造器包装 | **iv8 卡死** |
| `Uint8Array.prototype.set` | 无命中 |
| `Array.prototype.push` | 无命中 |
| `crypto.subtle.*` | **完全未被使用**（calls=[]） |
| `WebAssembly` 实例/memory | 未捕获到实例 |

差分实验（钉死 `Math.random`/`getRandomValues`/`Date`/`performance.now`）：
`st`/`sr`/`cr` 可完全一致，但载荷仍只有 ~11% 字节相同 → **链式加密/压缩**结构
（改 1 处会导致之后整段变化），前 **2739 字节**跨运行稳定。无 0x03 长游程 → canvas 被哈希而非原样存储。

**结论**：不反混淆 835KB 的 `challenge.js` 里的纯 JS 流密码，就拿不到明文；
继续调环境是盲猜。已用续期方案绕过。

## 七、已知限制与风险

1. **首次 token 必须来自真实浏览器**。`POST "null"` 只能拿到 `renewInSec=0` 的占位 token。
   本机已内置 Camoufox 自动 mint（`--mint`），约 15s。
2. **续期链需要保持存活**。建议在 `renewInSec` 的 ~60% 处续期；断链超过有效期就要重新 mint。
3. **air-bounds 偶发 403**（瞬时限流），重试 1~2 次即可。
4. **`x-d-token` 由 Imperva 校验**，OAuth 请求本身常是 `NNNN`（不校验），真正校验在 air-bounds。
5. **只读**：不下单、不占座、不支付。
6. **不落盘 secret**：token / access_token / client_secret / incap_* cookie 一律只存内存或环境变量。
